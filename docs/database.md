# PostgreSQL и миграции

## Настройки разработки

Локальный запуск описан в [README](../README.md).
Compose использует PostgreSQL 17, постоянный volume `postgres_data`,
health check и порт, доступный только на `127.0.0.1`.
Приложение и Compose читают локальный `.env`; опубликован только `.env.example`
с пустым полем пароля. Существующий `.env` при настройке сохраняется.

| Настройка | Назначение |
| --- | --- |
| `POSTGRES_DB` | Локальная БД; по умолчанию `payment_core` |
| `POSTGRES_USER` | Локальная роль; по умолчанию `payment_core` |
| `POSTGRES_PASSWORD` | Обязательный пароль для локального запуска |
| `POSTGRES_PORT` | Локальный порт; по умолчанию 5432 |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | Переопределение подключения приложения для внешней БД |

Для текущего dev-окружения приложение выполняет миграции с той же ролью,
которой обращается к данным. Разделение прав миграций и runtime относится
к production-настройке на этапе развёртывания.

## Начальная схема

Миграции находятся в `src/main/resources/db/migration`.
`V1__create_payment_core_schema.sql` создаёт:

| Таблица | Назначение |
| --- | --- |
| `users` | Нормализованный уникальный email, хеш пароля и роль |
| `ledger_accounts` | RUB-счета CUSTOMER/SYSTEM и оперативные остатки |
| `wallets` | Один RUB-кошелёк на пользователя и отдельный CUSTOMER-счёт |
| `payments` | TOP_UP/TRANSFER/REFUND, POSTED/REJECTED, исходный платёж возврата |
| `ledger_transactions` | Одна денежная транзакция на платёж |
| `ledger_entries` | Знаковые проводки с привязкой к счёту и транзакции |
| `idempotency_records` | Область ключа, отпечаток и сохранённый HTTP-результат |
| `audit_events` | Структурированные события с JSONB-данными |

Пользователи, администратор, технический счёт и тестовые средства автоматически
не создаются. Их сценарии относятся к последующим этапам.

JPA-сущности используют UUID-ссылки между модулями и `Instant` для времени.
Схему создаёт только Flyway; Hibernate запускается в режиме `validate`.
Изменения схемы после применения миграции оформляются новой версией SQL-файла.

## Ограничения БД

- Суммы платежей положительны; валюта счетов, кошельков и платежей — RUB.
- CUSTOMER-счёт имеет неотрицательный остаток. Отрицательный остаток разрешён SYSTEM.
- Составной внешний ключ не позволяет связать пользовательский кошелёк с SYSTEM-счётом.
- Кошелёк уникален для пользователя и валюты, его счёт уникален.
- У POSTED нет причины отказа; у REJECTED причина обязательна.
- POSTED не может иметь одинаковые исходный и принимающий счета;
  REJECTED с причиной SELF_TRANSFER допускается.
- REFUND ссылается на исходный платёж; только один POSTED REFUND разрешён
  на исходную операцию. Отклонённые попытки этому не препятствуют.
- Ключ идемпотентности уникален по инициатору, типу команды и тексту ключа.
- Зарезервированный ключ ещё не имеет результата; завершённая запись содержит
  HTTP-статус, JSON-объект ответа и ссылку на платёж.
- Внешние ключи защищают ссылки; индексы поддерживают историю и связи возвратов.

Ограничения проверяют структуру данных. Сбалансированная пара проводок,
неизменяемость проведённого журнала, совпадение остатков с проводками,
права инициатора и атомарное проведение будут реализованы механизмом учёта
и соответствующими миграциями на следующих этапах.
Наличие таблиц не означает готовности денежного API.

## Проверки

Тесты используют настоящий PostgreSQL через Testcontainers с образом
`postgres:17-alpine`. Они проверяют запуск Flyway с пустой схемой и повторную
проверку миграций, ограничения, связи, условия возвратов, область ключей
и сохранение/чтение JPA-моделей. HTTP-интеграционные проверки также загружают
полное приложение с PostgreSQL и включённой проверкой схемы.

Для ручной проверки локального повторного запуска:

1. Запустить Compose и приложение по README.
2. Проверить health и наличие записи Flyway в `flyway_schema_history`.
3. Остановить и снова запустить приложение: повторное применение V1 не требуется.
4. Перезапустить сервис `docker compose restart postgres`, дождаться health
   и снова проверить подключение приложения.

`docker compose down` сохраняет данные в volume. Резервное копирование,
проверка восстановления и production-права входят в этап развёртывания.
