# PostgreSQL и миграции

## Настройки разработки

Локальный запуск описан в [README](../README.md).
Compose использует PostgreSQL 17, постоянный volume `postgres_data`,
health check и порт, доступный только на `127.0.0.1`.
Приложение и Compose читают локальный `.env`; опубликован только `.env.example`
с пустым полем пароля. Существующий `.env` при настройке сохраняется.

| Настройка | Назначение |
| --- | --- |
| `POSTGRES_DB` | Локальная БД; по умолчанию `payment_core` |
| `POSTGRES_USER` | Локальная роль; по умолчанию `payment_core` |
| `POSTGRES_PASSWORD` | Обязательный пароль для локального запуска |
| `POSTGRES_PORT` | Локальный порт; по умолчанию 5432 |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | Переопределение подключения приложения для внешней БД |
| `JWT_SECRET` | Обязательный случайный Base64-ключ подписи JWT; не менее 32 байт после декодирования |

Для текущего dev-окружения приложение выполняет миграции с той же ролью,
которой обращается к данным. Разделение прав миграций и runtime относится
к production-настройке на этапе развёртывания.

## Миграции схемы

Миграции находятся в `src/main/resources/db/migration`.
`V1__create_payment_core_schema.sql` создаёт:

| Таблица | Назначение |
| --- | --- |
| `users` | Нормализованный уникальный email, хеш пароля и роль |
| `ledger_accounts` | RUB-счета CUSTOMER/SYSTEM и оперативные остатки |
| `wallets` | Один RUB-кошелёк на пользователя и отдельный CUSTOMER-счёт |
| `payments` | TOP_UP/TRANSFER/REFUND, POSTED/REJECTED, исходный платёж возврата |
| `ledger_transactions` | Одна денежная транзакция на платёж |
| `ledger_entries` | Знаковые проводки с привязкой к счёту и транзакции |
| `idempotency_records` | Область ключа, отпечаток и сохранённый HTTP-результат |
| `audit_events` | Структурированные события с JSONB-данными |

`V2__identity_sessions.sql` добавляет `refresh_sessions`: пользователь, хеш
refresh token, абсолютный срок и отметка отзыва. Исходный токен в БД не хранится.
`V3__ledger_integrity.sql` добавляет защиту журнала и проверки при commit.
`V4__idempotency_and_simulator.sql` создаёт выделенный технический RUB-счёт симулятора и
усиливает сохранность завершённых результатов идемпотентности. Другие
`SYSTEM`-счета допустимы: приложение использует именно выделенный счёт.
V1 уже применялась в ранее созданных БД; V2–V4 накладываются поверх неё.
Применённые миграции не переписываются.

Пользователи регистрируются явно. Администратор создаётся отдельной локальной
командой с учётными данными из переменных окружения. Выделенный технический
счёт симулятора создаётся миграцией с нулевым остатком; тестовые средства
возникают только при административном пополнении.

JPA-сущности используют UUID-ссылки между модулями и `Instant` для времени.
Схему создаёт только Flyway; Hibernate запускается в режиме `validate`.
Изменения схемы после применения миграции оформляются новой версией SQL-файла.

## Ограничения БД

- Суммы платежей положительны; валюта счетов, кошельков и платежей — RUB.
- CUSTOMER-счёт имеет неотрицательный остаток. Отрицательный остаток разрешён SYSTEM.
- Составной внешний ключ не позволяет связать пользовательский кошелёк с SYSTEM-счётом.
- Кошелёк уникален для пользователя и валюты, его счёт уникален.
- У POSTED нет причины отказа; у REJECTED причина обязательна.
- POSTED не может иметь одинаковые исходный и принимающий счета;
  REJECTED с причиной SELF_TRANSFER допускается.
- REFUND ссылается на исходный платёж; только один POSTED REFUND разрешён
  на исходную операцию. Отклонённые попытки этому не препятствуют.
- Ключ идемпотентности уникален по инициатору, типу команды и тексту ключа.
- Зарезервированный ключ ещё не имеет результата; завершённая запись содержит
  HTTP-статус, JSON-объект ответа и ссылку на платёж.
- Внешние ключи защищают ссылки; индексы поддерживают историю и связи возвратов.

V4 требует завершённый ответ для сохранённого ключа и запрещает изменение
готового результата. Ключ резервируется и результат завершается в той же
PostgreSQL-транзакции, что платёж, проводки и остатки; уникальность
`(actor_id, command_type, idempotency_key)` выдерживает конкурентный повтор.

V3 запрещает изменение и удаление платежей, кошельков и проведённых записей
журнала. Новые проводки разрешены только в транзакции создания журнала. Отложенные
триггеры при commit проверяют ровно одну транзакцию и две соответствующие
проводки для `POSTED`, отсутствие транзакции для `REJECTED` и равенство остатка
сумме проводок. Перед установкой защиты V3 проверяет существующие данные и
прерывает миграцию при расхождении, не исправляя деньги автоматически.
Внутренний сервис блокирует затрагиваемые счета в стабильном порядке
`FOR NO KEY UPDATE` и меняет остатки в той же транзакции, что платёж и журнал.
Проверки полномочий выполняются приложением. Пополнение, перевод и полный
возврат используют эти ограничения вместе с записью платежа, результата ключа
и аудита в одной транзакции. Возврат блокирует исходный платёж перед счетами,
создаёт отдельный `REFUND` с обратными проводками и сохраняет
`original_payment_id` как при `POSTED`, так и при `REJECTED`. Частичный
уникальный индекс V1 `payments_one_posted_refund_per_original` запрещает
второй успешный возврат исходной операции; отклонённые попытки не занимают его.
Для этапов 8–9 новая миграция не требуется.

История кошелька читает проведённые `ledger_entries` его счёта с привязкой
к платежу и стабильной сортировкой по времени и ID платежа. Сверка выполняется
в read-only транзакции с изоляцией `REPEATABLE READ`, чтобы все её запросы
видели один снимок PostgreSQL. Суммы проводок считает `NUMERIC`, сохраняя
возможность обнаружить расхождение без переполнения `BIGINT`; отчёт не
обновляет остатки и журнал.

## Проверки

Тесты используют настоящий PostgreSQL через Testcontainers с образом
`postgres:17`. Они проверяют запуск Flyway с пустой схемой и повторную
проверку миграций, ограничения, связи, условия возвратов, область ключей
и сохранение/чтение JPA-моделей. Тесты этапов 4–5 дополнительно проверяют
защиту сессий, права доступа, полное проведение, откат и конкурентные запросы.
Тесты этапов 8–9 проверяют обратные проводки, права и конкурентные возвраты,
историю только проведённых движений и обнаружение расхождений в изолированной
тестовой БД.
HTTP-интеграционные проверки загружают полное приложение с PostgreSQL и
включённой проверкой схемы.

Для ручной проверки локального повторного запуска:

1. Запустить Compose и приложение по README.
2. Проверить health и наличие записи Flyway в `flyway_schema_history`.
3. Остановить и снова запустить приложение: повторное применение V1–V4 не требуется.
4. Перезапустить сервис `docker compose restart postgres`, дождаться health
   и снова проверить подключение приложения.

`docker compose down` сохраняет данные в volume. Резервное копирование,
проверка восстановления и production-права входят в этап развёртывания.
