# Спецификация MVP: Payment Core v0.1.0

Статус: бизнес-правила и целевой контракт v0.1.0.
Документ определяет поведение версии. Подготовлены инфраструктура этапов 2–3,
авторизация и кошельки с внутренним механизмом учёта этапов 4–5.
Этапы 6–7 добавили идемпотентность, тестовое пополнение, перевод и чтение
отдельного платежа. Этапы 8–9 добавили полный возврат, историю и сверку.

## 1. Назначение и границы

Система учитывает тестовые средства в рублёвых кошельках пользователей.
Первая версия поддерживает регистрацию и вход, открытие кошелька,
административное тестовое пополнение, перевод, полный возврат, историю и сверку.

Все компоненты входят в одно модульное Spring Boot-приложение с PostgreSQL.
Клиентами первой версии служат Swagger UI и инструменты HTTP-запросов.
Получатель сообщает отправителю UUID своего кошелька самостоятельно.

Банковские интеграции, реальные списания, карточные данные, комиссии,
частичные возвраты, резервирование средств и обмен валют относятся к развитию
после `v0.1.0`. Сервис не запрашивает и не хранит данные банковских карт.

## 2. Роли и доступ

| Участник | Разрешённые действия |
| --- | --- |
| Неаутентифицированный клиент | Регистрация и вход; обновление/отзыв сессии по валидному refresh token |
| `USER` | Работа со своим кошельком; перевод со своего кошелька; полный возврат полученного перевода; просмотр доступных операций |
| `ADMIN` | Возможности `USER`, административное тестовое пополнение и служебная сверка |

Регистрация всегда создаёт `USER`. Назначение `ADMIN` выполняется отдельной
административной командой; поле роли не принимается при регистрации.
Администратор проводит обычные переводы и возвраты по тем же правилам владения,
что и пользователь.

Проверка личности и прав выполняется на каждом запросе, включая идемпотентный
повтор. Знание UUID или `Idempotency-Key` не предоставляет доступа.

- Кошелёк и его история доступны владельцу.
- В переводе допускается UUID кошелька другого пользователя как получателя.
  Это разрешает зачисление, но не чтение чужого баланса, истории или профиля.
  Отправляющий кошелёк принадлежит инициатору.
- Проведённый платёж доступен инициатору и владельцам участвующих пользовательских счетов.
- Отклонённый платёж доступен только инициатору: получатель не видит чужие неудачные попытки.
- Недоступный объект возвращает `404 RESOURCE_NOT_FOUND`, как и отсутствующий.
- Отсутствие валидной аутентификации возвращает `401 UNAUTHENTICATED`.
- Отсутствие административной роли на административном маршруте возвращает `403 FORBIDDEN`.

## 3. Денежные значения и ограничения

Единственная валюта — `RUB`. У пользователя может быть один RUB-кошелёк.
Суммы в API передаются целыми числами копеек и хранятся как Kotlin `Long`
и PostgreSQL `BIGINT`.

```json
{
  "amountMinor": 15000,
  "currency": "RUB"
}
```

Этот пример означает 150 рублей. Денежная арифметика не использует `Float`
или `Double`. Дробное JSON-число, в том числе `15000.0`, недопустимо.
Сумма команды должна быть положительной и помещаться в `Long`.
Валюта передаётся строго как `RUB`; неизвестные поля команды отклоняются.

Начальное настраиваемое ограничение `max-operation-amount-minor`:
`100000000` копеек, то есть 1 000 000 рублей. Оно применяется к `TOP_UP`
и `TRANSFER`. Возврат использует точную исходную сумму независимо от последующего
изменения этого лимита.

Все изменения остатков проверяются на переполнение, включая технический счёт.
Превышение денежного диапазона не допускает частичного проведения.

## 4. Учёт и инварианты

`Payment` описывает бизнес-операцию. `LedgerTransaction` группирует её денежные
проводки, а `LedgerEntry` фиксирует знаковое изменение конкретного счёта.
`Wallet` связывает пользователя с его учётным счётом.
Кошелёк создаётся атомарно с отдельным пользовательским счётом с нулевым
остатком. У этого счёта один кошелёк; владелец и валюта кошелька в MVP неизменны.

Обязательные правила:

1. Для каждой проведённой денежной транзакции сумма проводок равна нулю в RUB.
2. Пользовательский остаток всегда неотрицателен.
3. Каждому `POSTED`-платежу соответствует одна денежная транзакция.
4. У `REJECTED`-платежа нет денежной транзакции и проводок.
5. Проводки, остатки, статус платежа и результат идемпотентности фиксируются атомарно.
6. Оперативный остаток счёта равен сумме его проводок с момента открытия.
7. Проведённый журнал не редактируется, не удаляется и не дополняется задним числом.
8. Исправление движения выполняется новой связанной компенсирующей операцией.
9. Каждая проведённая операция MVP содержит ровно две проводки по разным счетам:
   `-amountMinor` на исходном и `+amountMinor` на принимающем.

Все финансовые команды используют один механизм проведения, без прямого изменения
остатка контроллерами или обходных административных списаний.

Для симуляции пополнений создаётся отдельный технический счёт. Ему разрешён
отрицательный остаток, который отражает выданные тестовые средства.
Это исключение не распространяется на пользовательские счета.

Пример последовательности, все значения в копейках:

| Состояние | Технический счёт | Кошелёк A | Кошелёк B |
| --- | ---: | ---: | ---: |
| Открытие счетов | 0 | 0 | 0 |
| Пополнение A на 1000 рублей | -100000 | 100000 | 0 |
| Перевод A → B на 250 рублей | -100000 | 75000 | 25000 |
| Полный возврат B → A | -100000 | 100000 | 0 |

В каждом состоянии сумма остатков этих счетов равна нулю.

## 5. Типы операций и состояния

| Тип | Назначение | Инициатор |
| --- | --- | --- |
| `TOP_UP` | Технический счёт → кошелёк | `ADMIN` |
| `TRANSFER` | Пользовательский кошелёк → другой кошелёк | Владелец отправляющего кошелька |
| `REFUND` | Обратное движение на точную сумму исходного перевода | Получатель исходного перевода |

| Статус | Денежный результат |
| --- | --- |
| `POSTED` | Операция проведена полностью |
| `REJECTED` | Ожидаемый бизнес-отказ; остатки не изменены |

Первая версия синхронная: в БД сохраняется окончательный результат команды.
Долговечные промежуточные состояния не требуются. Идентификаторы создаёт сервер
в формате UUID; время хранится в UTC и возвращается в ISO 8601.

Возврат создаёт отдельный `REFUND`-платёж с `originalPaymentId`.
Исходный перевод остаётся `POSTED`. Факт успешного возврата определяется
связанной проведённой операцией.

## 6. Целевой API

Маршруты auth, users/me и wallets реализованы на этапах 4–5; пополнение,
перевод и чтение отдельного платежа — на этапах 6–7; возврат, история и
сверка — на этапах 8–9. Схема реализованной части —
[OpenAPI](openapi.json), подробности сессий и запросов — [примеры API](api.md).

| Метод и путь | Назначение / доступ |
| --- | --- |
| `POST /api/v1/auth/register` | Создать `USER` |
| `POST /api/v1/auth/login` | Получить сессию |
| `POST /api/v1/auth/refresh` | Обновить сессию по refresh token |
| `POST /api/v1/auth/logout` | Отозвать refresh token |
| `GET /api/v1/users/me` | Текущий пользователь |
| `POST /api/v1/wallets` | Открыть собственный RUB-кошелёк |
| `GET /api/v1/wallets/me` | Собственные кошельки |
| `GET /api/v1/wallets/{id}` | Свой кошелёк и `balanceMinor` |
| `POST /api/v1/admin/top-ups` | Тестовое пополнение; `ADMIN`, обязательный ключ |
| `POST /api/v1/payments/transfers` | Перевод; обязательный ключ |
| `POST /api/v1/payments/{id}/refund` | Полный возврат; обязательный ключ |
| `GET /api/v1/payments/{id}` | Доступный платёж, включая собственный отказ |
| `GET /api/v1/wallets/{id}/transactions` | Проведённая история своего кошелька |
| `GET /api/v1/admin/reconciliation` | Синхронный отчёт сверки; `ADMIN`, без денежных изменений |

Команда пополнения:

```json
{
  "walletId": "11111111-1111-4111-8111-111111111111",
  "amountMinor": 100000,
  "currency": "RUB"
}
```

Команда перевода:

```json
{
  "fromWalletId": "11111111-1111-4111-8111-111111111111",
  "toWalletId": "22222222-2222-4222-8222-222222222222",
  "amountMinor": 25000,
  "currency": "RUB"
}
```

Для возврата тело отсутствует либо равно `{}`. Сумма, валюта и направление
определяются исходным переводом; дополнительные поля отклоняются.

Успешная денежная команда возвращает HTTP `201` и платёж: как минимум `id`,
`type`, `status`, `amountMinor`, `currency`, `createdAt` и, для возврата,
`originalPaymentId`. Сохраняемый бизнес-отказ возвращает HTTP `409`, `code`
и `paymentId`, по которому инициатор может получить `REJECTED`-платёж.

## 7. Идемпотентность

Каждая команда `TOP_UP`, `TRANSFER` и `REFUND` требует `Idempotency-Key`.
Рекомендуется UUID. Допустимый формат — `[A-Za-z0-9._:-]{1,128}`;
ключ регистрозависим и не содержит пробелов.

Область уникальности: `(actorId, commandType, idempotencyKey)`.
Внутри неё ключ не переиспользуется для новой операции. Одинаковый ключ другого
пользователя или другого типа команды относится к отдельной области.
В MVP результаты сохраняются без автоматического удаления.

Для ключа хранится отпечаток нормализованной команды. Он включает тип команды,
инициатора, участвующие UUID, сумму и валюту, когда они передаются.
Для возврата обязателен UUID исходного платежа из пути запроса.
Порядок JSON-полей не влияет на отпечаток; исходный текст JSON не используется
как единственный способ сравнения команд.

Порядок обработки:

1. Проверить актуальную аутентификацию и полномочия инициатора.
2. Проверить формат ключа, JSON, UUID, положительную целую сумму и валюту;
   разрешить ссылки с учётом правил операции. Для перевода проверить владение
   отправляющим кошельком и существование получающего: владение получающим
   кошельком не требуется. Для возврата проверить доступ к исходной операции
   и владение её получающим счётом.
3. В транзакции зарезервировать ключ или получить результат конкурентного запроса.
4. Для существующего ключа сравнить нормализованную команду.
   При совпадении вернуть сохранённые HTTP-статус и тело; при различии вернуть конфликт.
5. Только для новой команды проверить изменяемые бизнес-условия и провести операцию.
6. Сохранить результат в той же транзакции.

Проверка повтора выполняется до повторной проверки остатка, лимита операции
и наличия успешного возврата. Например, повтор успешного возврата с прежним
ключом возвращает прежний успех.

| Ситуация | Поведение |
| --- | --- |
| Прежний ключ и прежняя команда | Прежний HTTP-статус и сохранённое тело, без новых платежей и проводок |
| Прежний ключ и другая команда | `409 IDEMPOTENCY_CONFLICT`; прежняя запись сохраняется |
| Два конкурентных одинаковых запроса | Один денежный эффект; второй дожидается результата первого |
| Первый запрос откатился до commit | Его ключ и денежные изменения не фиксируются; повтор может выполнить команду |
| Ответ потерян после commit | Повтор возвращает уже сохранённый результат |
| Недостаточно средств | Сохраняются `REJECTED` и ответ; прежний ключ возвращает тот же отказ после пополнения |

Для новой попытки после бизнес-отказа используется новый ключ.
Воспроизводимый ответ не генерирует заново UUID и даты. Служебные HTTP-заголовки
отдельного запроса могут отличаться.

## 8. Атомарность и конкурентные запросы

Одна транзакция PostgreSQL включает ключ, необходимые блокировки, решение
о результате, платёж, проводки, остатки и событие аудита результата.
HTTP-успех отправляется после успешной фиксации транзакции.

Изменяемые счета блокируются через `SELECT … FOR NO KEY UPDATE` в стабильном порядке
по неизменяемому ID. Доступные средства проверяются после получения блокировки.
Этот порядок используется пополнениями, переводами и возвратами. Блокировка
`NO KEY UPDATE` защищает остатки и совместима с `KEY SHARE` внешних ключей
платежа; ключевые поля счёта неизменны.
Для возврата сначала блокируется исходный платёж, затем счета.

Уникальное ограничение защищает область ключа идемпотентности. Для конкурентного
захвата используется `INSERT … ON CONFLICT DO NOTHING` или эквивалентный алгоритм,
сохраняющий работоспособность текущей транзакции.

При ожидаемом бизнес-отказе фиксируются платёж `REJECTED`, ответ и аудит,
без проводок. Техническое исключение откатывает незавершённую транзакцию;
его диагностика не создаёт фиктивный `REJECTED`-платёж.
Разрыв связи во время commit может оставить клиенту неизвестный результат.
Неопределённость разрешается повтором с тем же ключом.

Внешние HTTP-вызовы не выполняются внутри денежной транзакции.
Аудит и диагностические логи содержат идентификаторы и результат действия;
пароли, токены и ключи подписи в них не попадают.

## 9. Правила полного возврата

Условия новой команды возврата:

- Инициатор — владелец получающего счёта исходной операции.
- Исходная операция имеет тип `TRANSFER` и статус `POSTED`.
- Для неё ещё нет успешного полного возврата.
- У получателя достаточно текущих средств на полную исходную сумму.
- Обратные изменения остатков не вызывают переполнения.

Возврат выполняет обратное движение между исходными счетами в той же валюте.
Возврат пополнения или другого возврата не поддерживается.

Если получатель потратил средства, новая команда возврата получает
`409 INSUFFICIENT_FUNDS`, статус `REJECTED` и не меняет остатки.
После пополнения новая попытка с новым ключом допустима.

Ограничение БД допускает не более одного `POSTED`-возврата на исходный перевод.
Отклонённые попытки не занимают это ограничение. При двух новых конкурентных
возвратах один может завершиться успешно, второй получает
`409 PAYMENT_ALREADY_REFUNDED` после проверки под блокировкой.
Повтор с ключом уже успешной команды возвращает её сохранённый успех.

## 10. Контракт ошибок

Ответ ошибки имеет тип `application/problem+json` и поля `type`, `title`,
`status`, `detail`, `instance`, `code`, `traceId`.
Для сохраняемого бизнес-отказа добавляется `paymentId`.
Клиент ориентируется на `code`, а не на текст сообщения.

| HTTP | `code` | Смысл | Сохраняется как `REJECTED` |
| --- | --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Некорректный JSON, поля, UUID, сумма или валюта | Нет |
| 400 | `INVALID_IDEMPOTENCY_KEY` | Отсутствующий или некорректный ключ денежной команды | Нет |
| 401 | `UNAUTHENTICATED` | Отсутствует валидная аутентификация | Нет |
| 403 | `FORBIDDEN` | Нет нужной роли на административном маршруте | Нет |
| 404 | `RESOURCE_NOT_FOUND` | Объект отсутствует либо недоступен инициатору | Нет |
| 405 | `METHOD_NOT_ALLOWED` | Метод не поддерживается маршрутом | Нет |
| 406 | `NOT_ACCEPTABLE` | Запрошенный формат ответа не поддерживается | Нет |
| 413 | `PAYLOAD_TOO_LARGE` | Превышен допустимый размер запроса | Нет |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Тип тела запроса не поддерживается | Нет |
| 409 | `EMAIL_ALREADY_EXISTS` | Email уже зарегистрирован | Нет |
| 409 | `WALLET_ALREADY_EXISTS` | У пользователя уже есть RUB-кошелёк | Нет |
| 409 | `IDEMPOTENCY_CONFLICT` | Прежний ключ используется с другой командой | Нет |
| 409 | `SELF_TRANSFER` | Перевод между одним и тем же кошельком | Да |
| 409 | `OPERATION_LIMIT_EXCEEDED` | Новое пополнение или перевод превышает настроенный лимит | Да |
| 409 | `BALANCE_LIMIT_EXCEEDED` | Изменение остатка выходит за диапазон учёта | Да |
| 409 | `INSUFFICIENT_FUNDS` | Недостаточно текущих средств | Да |
| 409 | `PAYMENT_NOT_REFUNDABLE` | Доступная исходная операция не является проведённым переводом | Да |
| 409 | `PAYMENT_ALREADY_REFUNDED` | Есть успешный полный возврат | Да |
| 503 | `TEMPORARILY_UNAVAILABLE` | Временная техническая недоступность | Нет |
| 500 | `INTERNAL_ERROR` | Неожиданная техническая ошибка | Нет |

Проверки доступа и формата предшествуют сохранению новой денежной команды.
Например, инициатор исходного перевода не получает права на возврат только
из-за доступа к его истории. Чужой возврат возвращает `404 RESOURCE_NOT_FOUND`.
Для владельца получающего счёта доступная операция неподходящего типа
отклоняется как `PAYMENT_NOT_REFUNDABLE`.

Ошибка формата, доступа или конфликт ключа не изменяет существующий денежный
результат и не занимает новый ключ. Техническая ошибка не сохраняется как
результат бизнес-отказа; повтор проводится с тем же ключом.
Сообщение ошибки не раскрывает SQL, stack trace или секреты.

## 11. История и сверка

История кошелька содержит только проведённые движения: идентификатор платежа,
тип, дату, валюту, знаковое изменение `deltaMinor` и связь с возвратом.
Отклонённая попытка доступна инициатору по `paymentId`, но не создаёт движение
в истории кошелька.

Пагинация: `page >= 0`, `size` по умолчанию 20, допустимо от 1 до 100.
Сортировка стабильная: время создания по убыванию, затем ID по убыванию.

Сверка вызывается через `GET /api/v1/admin/reconciliation` с ролью `ADMIN`
и выполняется синхронно в согласованном снимке БД. Она проверяет остатки по проводкам,
сбалансированность транзакций и отсутствие отрицательных пользовательских остатков.
Успешно выполненная проверка возвращает HTTP `200` и поля `consistent`,
`checkedAccounts`, `checkedLedgerTransactions`, `discrepancies`.
При найденных расхождениях `consistent=false`; один HTTP-статус не доказывает
корректность учёта. Техническая ошибка выполнения использует общий контракт ошибок.
Расхождение фиксируется для диагностики; автоматического исправления нет.

## 12. Сценарии приёмки

Сценарии ниже задают приёмку всей версии. Тесты этапов 4–9 покрывают регистрацию,
кошельки, инварианты учёта, идемпотентность, пополнение, перевод, возврат,
историю и сверку;
готовность остальных сценариев отслеживается в плане реализации.

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| MVP-01 | Регистрация с попыткой передать роль ADMIN | Запрос отклонён; самоназначение роли невозможно |
| MVP-02 | Пользователь открывает RUB-кошелёк, затем пытается открыть второй | Первый остаток 0; второй запрос — `WALLET_ALREADY_EXISTS` |
| MVP-03 | Пользователь запрашивает чужой кошелёк, историю или чужой отказ | `404`; данные не возвращаются |
| MVP-04 | USER вызывает административное пополнение | `403`; нет денежного эффекта и нового занятого ключа |
| MVP-05 | ADMIN пополняет A на 100000 копеек | A получает 100000; технический счёт -100000; один POSTED-платёж и сбалансированные проводки |
| MVP-06 | A переводит другому пользователю B 25000 при остатке A=100000, B=0 | A=75000, B=25000; платёж POSTED; сумма проводок 0; доступа к чтению чужого кошелька нет |
| MVP-07 | Нулевая, отрицательная, дробная сумма, сумма вне Long, неизвестная валюта или поле | `400`; нет платежей, проводок и занятого ключа |
| MVP-08 | Новая команда превышает настроенный лимит либо переполняет остаток | Соответствующий сохраняемый отказ; остатки прежние |
| MVP-09 | A переводит самому себе | `SELF_TRANSFER`; нет проводок |
| MVP-10 | Недостаток средств, затем пополнение и повтор с прежним ключом | Повтор возвращает прежний REJECTED; новая попытка с новым ключом может пройти |
| MVP-11 | Успешная команда повторяется с тем же ключом и иной очередностью JSON-полей | Те же HTTP-статус, тело и paymentId; одного денежного эффекта достаточно |
| MVP-12 | Один ключ используется с другой суммой или другим исходным ID возврата | `IDEMPOTENCY_CONFLICT`; прежний результат сохранён |
| MVP-13 | Одновременные одинаковые денежные команды при достаточных средствах | Один POSTED-платёж и один набор проводок; одинаковый результат запросов |
| MVP-14 | Два списания по 70000 с разными ключами при остатке 100000 | Один успех, один INSUFFICIENT_FUNDS; конечный остаток 30000 |
| MVP-15 | Искусственный сбой между действиями до commit | Полный rollback платежа, проводок, остатков, ключа и аудита результата |
| MVP-16 | Ответ потерян после commit либо исход commit неизвестен клиенту | Повтор с тем же ключом разрешает результат без повторного движения |
| MVP-17 | B возвращает полученные 25000 при достаточном остатке | Обратные проводки; REFUND POSTED; исходный TRANSFER остаётся POSTED |
| MVP-18 | Исходный отправитель пытается инициировать возврат | `404`; списания с получателя нет |
| MVP-19 | Получатель потратил часть суммы и запрашивает полный возврат | INSUFFICIENT_FUNDS; после пополнения допустима новая команда с новым ключом |
| MVP-20 | Два возврата исходного перевода с разными ключами выполняются одновременно | Один POSTED REFUND; второй PAYMENT_ALREADY_REFUNDED |
| MVP-21 | Успешный возврат повторяется с прежним ключом | Тот же успех; проверка наличия возврата не заменяет сохранённый результат |
| MVP-22 | Один текст ключа используется разными пользователями или типами команд | Независимые области ключей; правила доступа действуют в каждой |
| MVP-23 | После команды доступ инициатора к ресурсу отсутствует при повторе | Данные результата не раскрываются; актуальная проверка доступа обязательна |
| MVP-24 | Запрошен возврат пополнения или возврата, доступного получателю | PAYMENT_NOT_REFUNDABLE; новых проводок нет |
| MVP-25 | Сверка после успешных операций и после искусственного расхождения в тестовой БД | Корректный журнал проходит; расхождение обнаруживается без автоматической правки |
| MVP-26 | Перезапуск приложения и восстановление резервной копии в отдельную БД | Данные, результаты ключей и связи возвратов сохранены; сверка проходит |
| MVP-27 | Денежная команда с отсутствующим или некорректным ключом, затем корректный запрос | Первый ответ INVALID_IDEMPOTENCY_KEY без денежного эффекта; корректный запрос обрабатывается как новый |
| MVP-28 | После успешного перевода лимит снижен ниже его суммы; выполняется повтор и новая команда с новым ключом | Прежний ключ возвращает прежний успех; новый ключ получает OPERATION_LIMIT_EXCEEDED |
| MVP-29 | ADMIN вызывает сверку корректного журнала и журнала с тестовым расхождением; затем маршрут вызывает USER | Отчёты содержат consistent=true и consistent=false соответственно; USER получает FORBIDDEN |
