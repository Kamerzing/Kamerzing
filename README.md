# Payment Core

Учебное платёжное ядро на Kotlin и Spring Boot: рублёвые кошельки,
тестовые пополнения, переводы и полные возвраты с журналом денежных проводок.
Суммы в целевом API и базе выражаются целым числом копеек.

## Состояние проекта

Подготовлены спецификация MVP, структура модулей, единые HTTP-ошибки,
идентификаторы запросов, CI, PostgreSQL, миграции Flyway и JPA-модели.
Добавлены регистрация, JWT-сессии, роли, собственные RUB-кошельки и внутренний
механизм двойной записи. Этапы 6–7 добавили идемпотентные тестовые пополнения,
переводы и чтение отдельного платежа. Этапы 8–9 добавили полный возврат,
историю проведённых движений кошелька и административную сверку. Версия
`0.1.0` включает проверки надёжности, готовый Docker-образ, отдельный Compose
для сервера, резервное копирование и воспроизводимую демонстрацию.

- [Спецификация MVP](docs/mvp.md) — правила и сценарии приёмки.

- [Выпуск и развёртывание](docs/release.md) — образ, HTTPS, секреты, копирование и восстановление.

Реализованные маршруты описаны в [OpenAPI](docs/openapi.json) и

## Сборка и тесты

Нужны полный JDK 21 и работающий Docker Engine. На Windows/macOS можно
использовать Docker Desktop. Откройте корень проекта в IntelliJ IDEA.
В настройках IDEA выберите JDK 21 для Project SDK и Gradle JVM.
В терминале проверьте `java -version`: настройка SDK в IDEA не меняет системную
Java. При другой версии задайте `JAVA_HOME` на каталог установленного JDK 21
для текущего терминала перед запуском Wrapper.

Linux / macOS:

```bash
sh gradlew --no-daemon --max-workers=2 check build
```

Windows PowerShell:

```powershell
.\gradlew.bat --no-daemon --max-workers=2 check build
```

Тесты сами запускают изолированные PostgreSQL-контейнеры. Локальная Compose-БД
и `.env` для сборки не требуются. Недоступный Docker приводит к ошибке проверки;
интеграционные тесты не пропускаются автоматически.
HTML-отчёт: `build/reports/tests/test/index.html`.

## Локальный запуск

Все команды выполняются из корня проекта.

1. Создайте `.env`, сохранив существующий файл, если он уже есть.

   Linux / macOS:

   ```bash
   test -f .env || cp .env.example .env
   ```

   Windows PowerShell:

   ```powershell
   if (-not (Test-Path .env)) { Copy-Item .env.example .env }
   ```

2. В `.env` задайте собственный непустой `POSTGRES_PASSWORD` и `JWT_SECRET`.
   Для совместимости Docker Compose и Java properties используйте пароль
   из букв, цифр, `-` и `_` без кавычек и пробелов. `JWT_SECRET` — Base64
   от не менее 32 случайных байт. Пример генерации в PowerShell:

   ```powershell
   $jwtKeyBytes = New-Object byte[] 32
   [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($jwtKeyBytes)
   [Convert]::ToBase64String($jwtKeyBytes)
   ```

   Сохраните результат в `.env` как `JWT_SECRET=...` и не публикуйте ключ.
   Файл исключён из Git. Пустой ключ не позволяет запустить приложение.

3. Поднимите БД и дождитесь готовности:

   ```bash
   docker compose up -d --wait postgres
   ```

4. Запустите приложение:

   ```bash
   sh gradlew bootRun
   ```

   В Windows используйте `.\gradlew.bat bootRun`. Либо запустите
   `PaymentCoreApplication` в IDEA с рабочим каталогом, равным корню проекта.

Spring Boot читает `.env` как локальные properties. При запуске Flyway применяет
миграции, затем Hibernate проверяет схему через `ddl-auto=validate`.
Actuator `GET /actuator/health` на порту `8080` должен вернуть HTTP `200`
и `"status": "UP"`; проверка включает подключение к БД.

Для завершения приложения используйте `Ctrl+C`. Команда `docker compose down`
останавливает БД и сохраняет volume. Повторный `up` использует прежние данные.
Переменная `POSTGRES_PASSWORD` задаёт пароль при первом создании БД; его изменение
в `.env` не меняет пароль уже существующей роли PostgreSQL.

Внешнюю БД можно указать через `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`.
Настройки прокси, пароли и ключи передаются вне исходников.

## Авторизация и кошельки

Регистрация создаёт только `USER`; пароль хранится в BCrypt. Access JWT действует
до 15 минут и проверяется вместе с действующей сессией в БД на каждом запросе.
Refresh token меняется при каждом использовании, в БД хранится только его хеш.
Logout по текущему refresh token отзывает всю сессию, включая выданные access tokens.

Кошелёк создаётся с нулевым остатком и отдельным счётом в одной транзакции.
Повторное создание даёт `409 WALLET_ALREADY_EXISTS`; чужой кошелёк — `404`.
Обычные маршруты кошельков соблюдают владение и для `ADMIN`.
Примеры входа, открытия кошелька, обновления и завершения сессии: [docs/api.md](docs/api.md).

Сервис `LedgerPostingService` проводит платёж внутри уже открытой транзакции:
блокирует счета в одном порядке, проверяет остаток и переполнение, создаёт две
проводки и обновляет остатки. Миграция V3 проверяет полное проведение при commit
и запрещает изменение журнала. Возврат использует тот же механизм проведения.

## Пополнения, переводы, возвраты и повтор запроса

Денежная команда требует заголовок `Idempotency-Key`: от 1 до 128 символов
из `A–Z`, `a–z`, `0–9`, точки, подчёркивания, двоеточия и дефиса.
Один и тот же ключ в области пользователя и типа команды с теми же параметрами
возвращает сохранённый статус и результат без повторного движения денег.
Изменение параметров с прежним ключом даёт `409 IDEMPOTENCY_CONFLICT`.
Сохраняемый бизнес-отказ возвращает `409` и `paymentId`; новая попытка
после него требует новый ключ. Ошибка формата или прав не занимает ключ.

`POST /api/v1/admin/top-ups` доступен только `ADMIN`: средства поступают
из выделенного технического RUB-счёта на указанный кошелёк.
`POST /api/v1/payments/transfers` переводит деньги с собственного кошелька на
другой, не раскрывая отправителю остаток получателя. Сумма передаётся целым
числом копеек; начальный лимит одной новой операции — 100000000 копеек.
Успешная команда возвращает `201`, объект платежа и `Location`.
`POST /api/v1/payments/{id}/refund` позволяет получателю проведённого перевода
вернуть всю исходную сумму. Тело запроса отсутствует либо равно `{}`; сумму и
направление сервер берёт из исходного платежа. Успешный возврат создаёт новый
`REFUND` с `originalPaymentId` и обратными проводками, а исходный перевод
остаётся `POSTED`. Повтор с прежним ключом возвращает сохранённый результат;
на исходный перевод возможен только один успешный полный возврат.

`GET /api/v1/payments/{id}` показывает проведённый платёж инициатору и владельцам
участвующих кошельков, а отклонённый — только инициатору. Чужой платёж
возвращает `404`. `GET /api/v1/wallets/{id}/transactions` возвращает владельцу
только проведённые движения с пагинацией (`page` от 0, `size` от 1 до 100,
по умолчанию 20). `GET /api/v1/admin/reconciliation` доступен только `ADMIN`:
он сравнивает остатки с проводками и сообщает о расхождениях без исправления
денежных данных. Подробные запросы приведены в [примерах API](docs/api.md).

## Структура и диагностика

Модули организованы пакетами внутри одного приложения: `identity`, `wallet`,
`ledger`, `payment`, `audit`, `shared`. Доменные пакеты содержат JPA-модели,
сервисы авторизации, кошельков и проводок. HTTP-инфраструктура находится в `shared.web`.

Ошибки возвращаются как `application/problem+json`: `type`, `title`, `status`,
`detail`, `instance`, `code`, `traceId`. Сервер создаёт новый UUID запроса,
возвращает его в `X-Request-Id` и использует в логах. Значение входящего
`X-Request-Id` не принимается как доверенный идентификатор.
При повторе сохранённого денежного отказа тело сохраняет `traceId` исходной
команды; свежий `X-Request-Id` относится к текущему HTTP-запросу. SQL, сообщения
внутренних исключений и секреты в тело ошибки не попадают.
Неизвестные JSON-поля, дробные числа, строки (включая числовые)
и логические значения для целочисленных DTO отклоняются.

CI использует JDK 21 и `sh gradlew --no-daemon --max-workers=2 build`;
HTML-отчёты сохраняются как артефакт workflow. Для PR из форков секреты не нужны.

Для выпуска есть `Dockerfile`, `deploy/compose.prod.yaml`, Caddy и workflow
публикации в GHCR. Отдельный production Compose открывает только порты HTTPS
и HTTP для выдачи сертификата, хранит PostgreSQL в постоянном volume и
монтирует секреты из файлов. Скрипты `scripts/backup.sh` и
`scripts/restore-check.sh` проверяют копию в отдельной БД; `scripts/demo.py`
воспроизводит основной сценарий. Порядок и требования к серверу — в
[инструкции выпуска](docs/release.md). Локальный стек проверен; запуск на
целевом сервере ожидает доступ к нему и домен.
