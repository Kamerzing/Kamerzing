# Инструкции для агента: Kamerzing / payment-core

Эти правила действуют для проекта и его подкаталогов. Явные указания пользователя имеют приоритет. Более локальные `AGENTS.md` уточняют правила для своей области.

## Назначение проекта и общение

- Разрабатываем учебное платёжное ядро для финтех-портфолио: пользователи, рублёвые кошельки, тестовые пополнения, переводы, возвраты и денежный журнал.
- Объясняй работу по-русски, ясно и с учётом начинающего разработчика. Имена классов, методов и API сохраняй на английском.
- После изменений кратко сообщай, что сделано, как это работает, чем проверено и какие ограничения остались.
- Выполняй поставленную задачу до проверяемого результата. Самостоятельно решай обычные технические вопросы внутри согласованного объёма.
- Следуй выбранному этапу разработки; не начинай последующие этапы без соответствующей задачи.

## Как начинать работу

В начале каждой сессии прочитай корневые `AGENTS.md` и `LEARNING.md` и учитывай их на протяжении всей работы. При изменении этих файлов перечитай актуальную версию. `LEARNING.md` хранит подтверждённые уроки проекта: добавляй туда краткие выводы после выполненных задач, проверок или явных корректировок пользователя по правилам самого файла. Непроверенные идеи не считай обязательными инструкциями.

1. Проверь текущую папку, `git status`, ветку и существующие изменения пользователя.
2. Прочитай доступные `README.md`, `docs/mvp.md`, `docs/implementation-plan.md`, файлы сборки и CI; затем изучи затрагиваемый код и тесты.
3. `docs/mvp.md` — источник бизнес-правил. При расхождении с реализацией явно укажи проблему; не меняй финансовое поведение молча.

Репозиторий: `https://github.com/Kamerzing/payment-core`. Имя приложения: `payment-core`. Исторический облачный путь `/workspace/Kamerzing` не является локальным путём пользователя.

## Стек и архитектура

- Kotlin, JDK 21, Spring Boot, Gradle Kotlin DSL и Gradle Wrapper.
- PostgreSQL 17, Flyway, Spring Data JPA / Hibernate.
- JUnit 5, Testcontainers, Docker Compose, GitHub Actions.
- Spring Security для доступа; OpenAPI / Swagger для документации API по мере реализации соответствующих задач.
- Версии зависимостей определяй по актуальным файлам сборки. Не обновляй стек попутно с функциональной задачей.
- Архитектура — модульный монолит. Корневой пакет: `com.kamerzing.payment_core`; модули: `identity`, `wallet`, `ledger`, `payment`, `audit`, `shared`.
- Контроллеры принимают запросы и формируют ответы, сервисы выполняют сценарии и задают границы транзакций, репозитории работают с БД.
- Все денежные изменения проводи через общий механизм учёта. Не дублируй алгоритмы списания в разных контроллерах или сервисах.
- Следуй существующим соглашениям Kotlin и структуре проекта. Избегай несвязанных рефакторингов, лишних зависимостей и преждевременных абстракций.

## Денежные инварианты

- MVP работает с тестовыми средствами и валютой `RUB`. Суммы — `Long` в копейках; `Float` и `Double` для денег запрещены.
- Проверяй положительность суммы, лимиты операции и переполнение арифметики.
- У пользователя один рублёвый кошелёк. Перевод самому себе запрещён.
- Пользовательский остаток неотрицателен. Отрицательный остаток допустим только у технического счёта симулятора пополнений.
- Используй двойную запись: сумма проводок каждой денежной транзакции равна нулю. Проведённые записи журнала неизменяемы.
- Платёж, проводки, обновление остатков и результат идемпотентности фиксируются атомарно в PostgreSQL.
- `POSTED` означает полностью проведённую операцию; `REJECTED` — сохранённый бизнес-отказ без денежных проводок. Неожиданная техническая ошибка откатывает транзакцию.
- Блокируй затрагиваемые счета в стабильном порядке по идентификаторам. Проверяй актуальный остаток после получения блокировки.
- Не заменяй гарантии PostgreSQL блокировкой только в памяти процесса. Внешние ключи, уникальность и подходящие `CHECK`-ограничения дополняют проверки приложения.

## Идемпотентность и возвраты

- `Idempotency-Key` обязателен для `TOP_UP`, `TRANSFER`, `REFUND`; область ключа учитывает инициатора и тип команды.
- Одинаковый ключ с теми же нормализованными параметрами воспроизводит сохранённые HTTP-статус и результат. Другие параметры с прежним ключом дают конфликт.
- Последовательные и конкурентные повторы должны создавать один денежный эффект.
- Сохранённый бизнес-отказ воспроизводится даже после изменения баланса. Новая попытка требует нового ключа; технический сбой допускает повтор после отката.
- Повторная проверка прав обязательна и при воспроизведении результата.
- Полный возврат инициирует получатель исходного проведённого перевода. Сумму и направление определяет сервер по исходной операции.
- Возврат создаёт отдельный `REFUND` с обратными проводками; исходный перевод остаётся `POSTED`.
- На исходный перевод допускается не более одного успешного полного возврата, включая конкурентные запросы. Обеспечь защиту и ограничением БД.
- Отказ возврата из-за нехватки средств допускает новую попытку после пополнения с новым ключом.

## Доступ, ошибки и секреты

- Роли — `USER` и `ADMIN`. При регистрации нельзя назначить себе административную роль.
- Проверяй аутентификацию, роль и владение ресурсом на каждом запросе. Знание UUID или ключа идемпотентности не даёт доступа.
- Возможность перевести на чужой кошелёк не даёт права читать его баланс или историю. Пополнение симулятора и сверка доступны администратору.
- Хешируй пароли через `PasswordEncoder`. Для запланированной JWT-аутентификации проверяй подпись, срок и назначение токена; refresh token храни в виде хеша, поддерживай ротацию и отзыв.
- Единый контракт ошибок — `ProblemDetail` с `code` и `traceId`; придерживайся спецификации API.
- Не включай в ответы и логи пароли, токены, секреты подключения, SQL-диагностику и стек исключения. Сохраняй полезную диагностику без чувствительных данных.
- Секреты передавай через переменные окружения или предусмотренный механизм среды. В Git допускаются только шаблоны без реальных секретов.
- Учитывай пожелание пользователя применять Anthropic Cybersecurity Skills: выбирай доступные навыки по конкретной задаче, читай их инструкции и сообщай об использовании. Не запускай несвязанные сканирования или атаки из-за наличия навыка.

## База данных и миграции

- Схему меняй через новые миграции Flyway. Уже применённые миграции не переписывай.
- Hibernate используй с `ddl-auto=validate`; не полагайся на автоматическое изменение схемы.
- Учитывай существующие данные при добавлении ограничений и обязательных полей.
- Проверяй применение миграций на пустой БД, повторный запуск и соответствие JPA-моделей схеме.
- Не удаляй пользовательские БД, Docker volumes и данные ради исправления тестов или миграций.
- Сверка обнаруживает расхождения между остатками и журналом; автоматическое исправление денег в MVP не предусмотрено.

## Проверки изменений

- Используй Gradle Wrapper из корня приложения и JDK 21. Сначала уточни реальные задачи сборки по проекту и CI.
- Типичная полная проверка в PowerShell: `.\gradlew.bat check build`; в Linux/macOS: `./gradlew check build`.
- Перед интеграционными тестами проверь `docker info`. PostgreSQL, блокировки и миграции проверяй на настоящем PostgreSQL через Testcontainers; H2 не подтверждает эти гарантии.
- Добавляй содержательные тесты вместе с поведением. Для исправления ошибки добавляй проверку, воспроизводящую её, когда это применимо.
- Для денежных изменений проверяй атомарность и откат, сбалансированность проводок, отсутствие отрицательного пользовательского остатка, повторы и конкурентность затронутых сценариев.
- Для доступа проверяй чужие ресурсы и административные операции; для возвратов — права получателя, нехватку средств и конкурентный повтор.
- Конкурентные проверки должны использовать отдельные транзакции/соединения и управляемую синхронизацию.
- Не отключай тесты и ограничения ради зелёной сборки. Если Docker, сеть или JDK недоступны, укажи, какие проверки выполнены и какие остались неподтверждёнными.
- Для изменения только документации проверь содержание, ссылки и diff; сборку приложения запускай при необходимости.
