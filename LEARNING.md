# LEARNING.md — Память и уроки проекта

Этот файл помогает Codex учитывать **подтверждённый опыт предыдущих сессий**. Он относится только к текущему проекту.

**Правила ведения:**
- Читать в начале работы над проектом (см. `AGENTS.md`).
- Добавлять выводы только после реально выполненной задачи, проверки или явной корректировки пользователя.
- Записывать кратко: **контекст → правило/вывод → подтверждение**.
- Избегать повторов, устаревших записей, паролей, токенов и персональных данных.
- Если урок перестал быть актуальным, исправить или удалить запись с пояснением причины.
- Если подтверждённых уроков ещё нет, оставлять этот файл почти пустым.

## Подтверждённые уроки

### 2026-10-24 — Публикация локальной истории без файлов переписки

- Контекст: рабочая ветка содержала код и два исторических файла чата, а удалённый `main` отставал от локальной разработки.
- Правило: готовить ветку публикации от актуального удалённого `main`, переносить только нужные отслеживаемые файлы и проверять состав индекса до отправки.
- Подтверждение: отдельная ветка `codex/payment-core-v0.1.0` создана от `main`; файлы переписки исключены и добавлены в `.gitignore`.


### 2026-10-24 — Проверка выпускного образа и восстановления

- Контекст: этапы 10–12 потребовали проверить не только JAR, но и путь запуска из образа, секреты Compose и сохранность данных после перезапуска.
- Правило: собирать образ из JAR, прошедшего `check build`; выполнять демонстрацию и восстановление в отдельной БД, проверять журнал и запуск приложения на восстановленной схеме.
- Подтверждение: 80 тестов без ошибок; локальный Compose с HTTPS, полный демонстрационный сценарий, `pg_dump`/`pg_restore` с SQL-сверкой и перезапуск app/Caddy с сохранением 3 платежей. Серверная публикация не проверялась.

### 2026-10-24 — Возврат и согласованный снимок для сверки

- Контекст: этапы 8–9 добавили возврат, историю и административную сверку поверх денежного журнала этапов 6–7.
- Правило: для новой команды возврата блокировать исходный платёж до счетов, а сохранённый результат ключа воспроизводить до проверки изменяемых условий; чтение сверки выполнять в `REPEATABLE_READ` и не менять денежные данные.
- Подтверждение: интеграционные тесты на PostgreSQL проверили конкурентные ключи, отказы, откат, историю и расхождение; полная `check build` — 78 тестов без ошибок. Частичный индекс для одного `POSTED REFUND` уже был в V1.

### 2026-10-23 — Строгий JSON для целочисленных полей
- Контекст: Jackson 3.1.5 по умолчанию преобразовывал числовую строку в `Long`; запрета `accept-float-as-int` для этого недостаточно.
- Правило: для целочисленных полей запрещать coercion строк, пустых строк, дробных и логических значений через `JsonMapperBuilderCustomizer`, сохраняя настройки Spring Boot и Kotlin-модуль.
- Подтверждение: `JsonConfiguration.kt`, HTTP-тесты в `ApiHttpIntegrationTests.kt`; полная сборка — 31 успешный тест, без пропусков.

### 2026-10-23 — JDK терминала и настройки IDEA
- Контекст: системная Java была версии 26, а проект использует JDK 21. Нужный JDK уже был установлен отдельно.
- Правило: проверять Java в терминале и Gradle JVM в IDEA независимо; для команд сборки задавать `JAVA_HOME` на JDK 21 в текущем процессе, без изменения системной Java.
- Подтверждение: успешная локальная команда `gradlew.bat --no-daemon --max-workers=2 check build` с JDK 21; инструкция в README.

### 2026-10-23 — Публичные маршруты и фильтр Bearer
- Контекст: `permitAll` разрешает маршрут в Spring Security, но не отключает собственный фильтр Bearer; устаревший заголовок мешал обновить или отозвать сессию по действующему refresh token.
- Правило: фильтр Bearer пропускает публичные `POST /api/v1/auth/*`, где учётные данные проверяет сам сценарий; защищённые маршруты по-прежнему требуют действующий access token.
- Подтверждение: `SecurityConfiguration.kt`, тест refresh/logout с устаревшим Bearer в `IdentityHttpIntegrationTest.kt`; полная сборка — 55 успешных тестов.

### 2026-10-23 — Завершение идемпотентного платежа в одной транзакции
- Контекст: незавершённая резервация ключа и лишнее обновление JPA могли оставить или повредить сохранённый результат.
- Правило: фиксировать платёж, проводки, остатки, аудит и ответ ключа одной транзакцией; завершённую запись защищать ограничениями PostgreSQL и считать неизменяемой в JPA.
- Подтверждение: миграция V4, IdempotencyService, аннотация Immutable у IdempotencyRecordEntity; 69 успешных тестов и повторный запуск JAR на существующей Compose-БД после V3→V4.
